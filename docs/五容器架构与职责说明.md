# 五容器架构与职责说明

本文说明当前 Docker Compose 部署的组成、数据保存方式和运行边界。功能介绍、首次启动、网页操作和日常维护见 [README](README.md)。

这 5 个容器，是按**对外服务、后台处理、定时调度、长期存储、运行协调**这五种职责划分的。

这样划分主要是为了让团队使用时，上传文档、知识抽取、定时维护和日常问答能够分别运行，并且方便单独重启、扩容和排查问题。实际响应速度和并发能力需要结合服务器及模型服务测量。

先区分两个概念：

- **镜像**：安装好程序和依赖的“软件包”。
- **容器**：用这个软件包实际运行起来的一个实例。

所以目前是 **3 种镜像，运行出 5 个容器**：

| 镜像 | 启动的容器 |
| --- | --- |
| 项目应用镜像 | API、Worker、Scheduler |
| PostgreSQL + pgvector 镜像 | PostgreSQL |
| Redis 镜像 | Redis |

默认服务器配置通过接口连接生成和 Embedding 服务，也可配置重排服务。模型服务通常由外部服务或宿主机提供；选择本地模型适配器时，需要另行准备权重及计算资源。部署应用镜像不会自动部署独立的大模型推理服务。

## 1. API 容器：接待用户、提供网页和接口

这是用户直接访问的入口，目前通过 `8080` 端口提供服务。

**实际负责的工作：**

- 提供前端网页。
- 登录、身份验证和知识库权限检查。
- 文档上传、文档管理、成员管理。
- 知识问答和流式返回答案。
- 图谱查询、口语过滤、人工校正。
- 创建后台任务、查询任务进度。
- 提供智能体调用知识工具的接口。

例如，你上传一个 PDF，API 会接收文件、登记文档信息、创建处理任务，再把处理状态返回页面。

**为什么独立出来？**

用户操作需要及时响应，但解析一个大 PDF、执行 OCR、调用模型抽取图谱，可能持续较长时间。因此这些后台任务放到 Worker 中执行，API 可以继续处理其他用户的请求。

API 更新或重启时，也可以单独操作这个容器。

不过，**API 本身仍会执行实时计算和模型调用**。例如问答和口语图谱过滤就在用户请求过程中完成，API 中也有自己管理的 codecode 进程。

## 2. Worker 容器：执行耗时的后台工作

Worker 可以理解为项目的“后台作业执行器”。

**实际负责的工作：**

- 文档解析、OCR、切片。
- 生成和更新向量索引。
- 调用 codecode 识别实体、关系和别名。
- 图谱重建、社区维护。
- Schema 生成与变化分析。
- 数据源同步。
- 代码索引及相关向量更新。
- 执行排队的智能体工作流。
- 更新任务进度，处理重试和取消。

它运行的是独立入口：[run_worker.py](../scripts/run_worker.py)。

**为什么独立出来？**

这类工作与网页请求的特点不同：

| 网页请求 | 后台处理 |
| --- | --- |
| 希望尽快响应 | 可以排队执行 |
| 通常持续较短 | 可能持续几分钟甚至更久 |
| 关注用户等待时间 | 关注吞吐量、进度和恢复 |
| 并发随用户操作变化 | 需要控制批量和模型调用数量 |

独立之后，可以根据文档处理量调整 Worker 的数量和并发，而不用同时增加网页服务。

Worker 通过数据库中的任务领取和执行期限管理任务。进程异常退出后，过期任务可以被恢复处理。**这提供了恢复机制，但不代表所有外部操作天然只执行一次**，具体步骤仍需要保证可重复执行的安全性。

Worker 也运行自己的 codecode，运行状态和 API 中的 codecode 分开存放。

## 3. Scheduler 容器：检查什么时候需要自动做事

Scheduler 是“定时值班员”。

**当前负责的工作：**

- 检查哪些数据源到了同步时间，创建同步任务。
- 检查哪些图谱社区需要更新，安排维护任务。
- 按配置执行知识库定期备份和保留策略。
- 恢复异常中断后遗留的流式会话状态。

它运行的是：[run_scheduler.py](../scripts/run_scheduler.py)。

例如，每隔一段时间，它检查某个数据源是否需要同步；如果需要，就创建任务，由 Worker 执行后续同步处理。备份流程则包含 Scheduler 直接执行的操作。

这里的定期备份指知识库级备份；服务器完整备份由宿主机计划任务执行，操作方式见 [README](README.md)。

**为什么不放进 API 或 Worker？**

如果把定时检查附带在每个 API 中，将来增加多个 API 实例时，就可能有多个进程同时触发同一项计划任务。

如果附带在 Worker 中，定时维护的生命周期又会和后台作业绑定。

单独运行后，定时维护有清晰的入口和运行状态。项目还通过 Redis 中可续期的执行资格，协调由一个 Scheduler 承担当前调度工作。

**当前 Scheduler 不会自动启动 codecode**，因为它的主要职责是安排和维护任务。

## 4. PostgreSQL + pgvector 容器：保存长期数据

这是项目的主要数据库。

**当前保存的内容包括：**

- 用户、成员和权限。
- 知识库、文档信息、文档片段。
- 对话和消息记录。
- 后台任务、进度、执行状态。
- 图谱实体、关系、证据。
- Schema 和历史版本。
- 人工校正、个人图谱视图。
- 文档、实体、关系和代码等向量索引。

其中：

- **PostgreSQL** 提供普通业务数据存储和查询。
- **pgvector** 是安装在 PostgreSQL 内的向量扩展，所以它们合在一个容器里。

目前图谱也存储在 PostgreSQL 的相关表中。

**为什么数据库独立？**

数据库有自己的运行要求：事务、并发写入、索引、备份、恢复和版本升级。这些都需要独立管理。

应用代码更新时，只需要更换应用容器；数据库及其持久化数据可以继续保留。数据库文件放在独立的持久卷中。

另外，**原始 PDF、Word 等文件保存在共享文档存储卷中**，数据库主要保存文件记录及处理后的结构化内容。这个共享存储卷不会额外占用一个容器。

### 持久卷和宿主机目录

| 存储位置 | 内容 | 使用者 |
| --- | --- | --- |
| `postgres` 卷 | 主库、业务记录和四类向量 | PostgreSQL |
| `documents` 卷 | 原文件、历史版本、图片、应用内知识库备份 | API、Worker、Scheduler |
| `redis` 卷 | Redis 持久化数据 | Redis |
| `api-agents`、`worker-agents` 卷 | 各自独立的 codecode 配置、状态和会话 | 对应的 API 或 Worker |
| `search-cache` 卷 | 按内容哈希保存的关键词分词缓存 | API、Worker |
| 宿主机 `data/operations/` | 服务器备份状态等运维信息，以只读方式挂载 | API、Scheduler |

容器更新或重建时复用这些存储。完整服务器备份需要同时覆盖主库、原文件和配置，不能只复制项目的 `data/` 目录。删除 Docker 数据卷会删除其中的数据。

## 5. Redis 容器：提供快速通知和运行协调

Redis 主要保存需要快速访问、经常变化的运行信息。

**当前主要用途：**

- 通知 Worker 有新任务。
- 提供共享缓存。
- 记录 Worker 和 Scheduler 的存活心跳。
- 控制问答、图谱过滤等操作的并发数量。
- 协调 Scheduler 的执行资格。
- 提供共享登录尝试限制等运行状态。

**为什么已经有 PostgreSQL，还需要 Redis？**

两者承担的访问模式不同。

PostgreSQL 负责保存完整、可靠的业务记录；Redis 适合处理短时状态、快速通知和频繁协调。这样可以减少这些操作对业务数据库的压力。

这里有一个与恢复能力直接相关的设计：

**任务的正式记录和执行状态保存在 PostgreSQL 中。Redis 主要负责唤醒 Worker。**

因此，某一次 Redis 通知丢失后，Worker 仍可以扫描数据库，找到待处理任务。不过，Redis 故障期间，并发协调和部分业务操作仍会受到影响。

## 6. 为什么 API、Worker、Scheduler 共用一个应用镜像？

因为它们是**同一个项目的三种运行角色**，使用大量相同的代码：

- 相同的数据模型。
- 相同的数据库访问逻辑。
- 相同的业务服务。
- 相同的配置和权限规则。
- 相同的智能体适配层。

当前启动方式是：

| 容器 | 使用的镜像 | 启动内容 |
| --- | --- | --- |
| API | `rag-enterprise:team` | 网页和接口服务 |
| Worker | `rag-enterprise:team` | `scripts.run_worker` |
| Scheduler | `rag-enterprise:team` | `scripts.run_scheduler` |

Dockerfile 在构建阶段编译前端和固定版本的项目内 codecode，并安装后端及文档解析依赖。API 默认以单个 Uvicorn 主进程运行；Worker、Scheduler 分别使用独立 Python 入口。

启动脚本支持在部署机器上构建镜像。发布流程也会构建并测试实际生产镜像、审计 Python 依赖，成功后推送按完整提交号标识的镜像；通过 `.env.server` 的 `APP_IMAGE` 指定版本或摘要，服务器拉取后同时更新三个应用角色。基础镜像固定摘要，发布和回退操作见 README。

可以理解为：**同一套程序，启动时分别安排三个岗位。**

这样做有几个好处：

1. **版本一致。** API 创建的任务，Worker 使用同一版本的代码处理，减少字段、任务格式和业务规则不一致的问题。
2. **构建和交付简单。** 每次发布构建一个应用镜像，再用它更新三个角色，方便追踪版本和回退。
3. **共用依赖和业务代码。** 无须为三个角色分别维护一套安装流程。
4. **可以分别运行和扩容。** 共用镜像不会把它们绑成一个进程。三个容器的进程、重启和临时运行状态分别管理，共享数据则通过数据库、Redis 和挂载卷访问。
5. **同一台机器可以复用镜像文件。** Docker 会共享镜像中的只读文件层，不需要保存三套完整镜像。但各个进程消耗的内存仍然分别计算。

这个做法也有代价：**Scheduler 使用的镜像会包含它用不到的 OCR、文档解析和 codecode 等依赖，镜像体积偏大。** 当前优先保持版本和部署方式一致；以后如果镜像大小成为实际问题，可以再为不同角色制作精简镜像。

## 7. 一次操作中，五个容器怎样配合？

### 上传和入库

以“上传文档并抽取图谱”为例：

1. **API** 接收文件，检查权限，把原文件保存到共享文档存储。
2. **PostgreSQL** 保存文档记录和待处理任务。
3. **Redis** 通知 Worker 有任务可处理。
4. **Worker** 领取任务，解析、切片、生成向量，再调用 codecode 抽取知识。
5. **PostgreSQL** 保存片段、向量、实体、关系、证据和任务进度。
6. **API** 把进度和处理结果显示给用户。
7. **Scheduler** 在后续定时检查中安排同步、图谱维护或备份。

这个过程不要求每个容器每次都参与；例如普通图谱查询主要由 API 和数据库配合完成。

同一知识库的写入使用 PostgreSQL 跨进程锁协调，不同知识库可并行处理。任务进度和租约也保存在主库中，Redis 通知用于减少等待。

### 检索和生成回答

1. **API** 检查登录状态、知识库权限和本次回答范围。
2. **Redis** 分配共享的问答并发名额；暂时没有名额时，请求在配置的时限内等待。
3. **API** 按需改写问题，执行向量、关键词、图谱或代码检索，并融合、重排和整理引用。
4. **PostgreSQL + pgvector** 返回候选片段、图谱事实及相关元数据；关键词索引在应用进程内查询。
5. **模型服务** 根据检索上下文生成答案，**API** 将答案流和来源返回网页，并保存会话记录。
6. 回答流结束或取消后，释放相应并发名额。

普通实时问答直接由 API 处理；Worker 主要处理入库和维护任务。问答仍可能受后台任务的 CPU、内存、磁盘和模型额度占用影响，因此需要分别控制资源。

## 8. 资源边界与部署限制

**五个容器仍然运行在同一台服务器上，共享这台机器的 CPU、内存和磁盘。**

当前 Compose 已为五个服务设置 CPU、内存硬限制，默认值如下，可通过服务器环境配置覆盖：

| 服务 | CPU 上限 | 内存上限 | 对应环境变量 |
| --- | ---: | ---: | --- |
| API | 2 核配额 | 3 GiB | `API_CPUS`、`API_MEMORY` |
| Worker | 4 核配额 | 6 GiB | `WORKER_CPUS`、`WORKER_MEMORY` |
| Scheduler | 0.5 核配额 | 1536 MiB | `SCHEDULER_CPUS`、`SCHEDULER_MEMORY` |
| PostgreSQL | 2 核配额 | 3 GiB | `POSTGRES_CPUS`、`POSTGRES_MEMORY` |
| Redis | 0.5 核配额 | 512 MiB | `REDIS_CPUS`、`REDIS_MEMORY` |

这些是资源上限，并不代表服务器会为各服务独占预留对应的 CPU 和内存。API、Worker、Scheduler 停止时最多等待 90 秒，以便完成退出处理。

当前没有数据库主从或多机容灾。因此，这种划分方便独立管理和后续扩展；实际能支撑多少人，还取决于服务器配置、文档规模和模型服务能力。

### 并发与检索规模

- 上传文件暂存、数据库事务及等待同库锁均在线程内处理，ZIP 在 Worker 中校验和解压，避免占住 API 异步循环。任务及条目在同一事务发布，Redis 只负责唤醒，通知失败后 Worker 仍可从数据库领取。
- 监控在各进程内限量累积，后台批量同步 Redis；就绪检查验证连接和结构，全量索引一致性检查由管理员手动分批执行。
- 回答没有证据时直接拒答；通道失败、关键词超限、重排降级均返回诊断。模型及解析指纹不匹配的旧索引需从原件重建。

- 服务器模式默认允许同时执行 8 个完整问答请求，等待名额默认最长 30 秒；流式回答在结束前持续占用名额。
- 生成模型调用默认共享 8 个名额，后台模型任务最多占其中 2 个。Embedding 和重排服务的上游限流还需单独考虑。
- 每 Worker 默认同时处理 2 个任务；解析、向量、模型等任务还有各自的资源类别限制。
- BM25 默认每个应用进程最多缓存 8 个知识库，每库最多为 10 万个活动片段构建关键词索引。超过单库保护线后，关键词通道不可用，向量通道仍会尝试工作；数据库可存储的数据量与此保护配置是两回事。
- pgvector 默认精确查询。项目支持维护 HNSW 索引及显式启用近似查询，启用前需在真实语料上同时检查延迟、召回率及范围过滤结果。

这些数值是当前默认配置，不是“多少页、多少人一定不卡顿”的承诺。实际容量应使用目标服务器、代表性文档及真实模型做并发验收。

### 增加实例时需要处理的事项

- API 与 Worker 可以分别扩展，但每个实例都需要独立的 codecode 状态目录和可达的知识工具回调地址。
- 多实例共享 PostgreSQL、Redis 和原文件；跨主机时需把原文件存储适配为共享服务。
- Redis 中的问答和模型额度在实例之间共享，增加容器不会自动提高全局额度或模型供应方配额。
- 多个 API 进程会分别占用关键词索引内存，数据库连接数也随实例增加，需要一起规划。

具体配置见 [compose.yml](../deploy/compose.yml)、[Dockerfile](../Dockerfile) 和 [服务器配置示例](../deploy/server.env.example)。启动、停止、升级、备份与故障处理统一见 [README](README.md)。
