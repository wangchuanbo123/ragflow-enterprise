# 代码阅读指南

## 1. 先理解三个入口

项目有三个主要入口，它们分别处理在线问答、离线索引和质量评估。

| 入口 | 文件 | 作用 |
| --- | --- | --- |
| HTTP 服务 | `app/main.py` | FastAPI 生命周期、中间件、异常处理和路由注册 |
| 文档索引 | `scripts/ingest_documents.py` | 同步、重建、collection 管理和图谱构建命令 |
| RAG 评估 | `scripts/evaluate_rag.py` | retrieval/full 评估及结果对比 |

第一次阅读代码时，建议按“API -> Service -> RAG Node -> Provider/Store”的方向阅读。

## 3. 在线问答有两条调用路径

### 3.1 兼容接口 `/ask`

```text
app/api/routes.py
  -> app/services/rag_service.ask_question()
  -> rag/graph/rag_graph.build_graph()
  -> compiled_graph.invoke()
```

该路径真正执行编译后的 LangGraph，并通过 `get_current_user` 要求登录。

### 3.2 Web 聊天接口

```text
app/api/v1/messages.py
  -> app/services/chat_service.py
  -> app/services/rag_service.prepare_context()
  -> app/services/rag_service.generate()/stream_generate()
```

该路径复用节点函数，但由普通 Python 代码手工编排，没有调用编译后的 LangGraph。
因此当前项目属于“LangGraph + Service 手工编排”的混合架构。

## 4. 当前 LangGraph 节点

工作流定义在 `rag/graph/rag_graph.py`：

```text
rewrite -> retrieve -> rerank -> build_context -> generate -> END
```

| 节点 | 文件 | 输入重点 | 输出重点 |
| --- | --- | --- | --- |
| `rewrite` | `rag/nodes/rewrite_node.py` | 原问题、历史 | 原问题、改写问题、检索问题列表 |
| `retrieve` | `rag/nodes/retrieve_node.py` | 检索问题列表 | 融合候选文档 |
| `rerank` | `rag/nodes/rerank_node.py` | 原问题、候选文档 | 重排后的文档 |
| `build_context` | `rag/nodes/context_node.py` | 文档 | 有预算的上下文、引用来源 |
| `generate` | `rag/nodes/generate_node.py` | 原问题、历史、上下文 | 最终回答 |

知识图谱目前不是独立 LangGraph 节点。它位于 `retrieve` 内部，作为
`HybridGraphRetriever` 的第三条检索通道。

## 5. 检索链路

`RAGRuntime` 在第一次提问时加载：

```text
LLMProvider
EmbeddingProvider
Reranker
活动 Chroma collection
HybridGraphRetriever 或 HybridRRFRetriever
```

一次检索的主要步骤：

1. `rewrite` 产生 `[original_query, rewritten_query]`。
2. 每个查询执行向量检索和中文 BM25。
3. 图谱启用时执行实体匹配、最多二跳遍历并映射回证据 Chunk。
4. `weighted_rrf_fusion()` 按 `chunk_id` 去重和排序。
5. BGE Reranker 使用原始问题重排。
6. ContextBuilder 限制 Chunk 数、来源数和 Token 预算。

当前 `RAGState` 只有一个 `context` 字段，没有独立的
`text_context` 和 `graph_subgraph`。图谱事实暂存在 Document metadata 的
`graph_facts` 中。

## 6. 文档索引链路

```text
CLI/API
  -> IndexJob（API 请求时）
  -> IndexWorker
  -> DocumentIndexService / IndexManager
  -> Loader
  -> Chunker
  -> Chroma + knowledge_documents + knowledge_chunks
```

核心数据标识：

- `document_id`：文档 UUID。
- `file_hash`：文件内容 SHA-256。
- `chunk_id`：由 document、file hash、schema version 和序号确定性生成。
- `active_collection_name`：保存在 `knowledge_index_state`。

全量重建先处理全部磁盘文档并写入影子 collection，数量和 ID 全部校验通过后，
才在一个 SQLite 事务中替换 Chunk 并切换活动指针。单文件更新先写新向量和
SQLite，再清理旧向量；失败时旧索引保持可用。真实数据是否已经完成重建请查看
[当前实现状态](当前实现状态.md)。

## 7. 知识图谱链路

构建：

```text
--graph-only
  -> GraphBuildService
  -> pending KnowledgeChunk
  -> GraphExtractor
  -> 当前 LLM Provider（glm-5.2）
  -> Pydantic/证据校验
  -> SqliteGraphStore
  -> kg_entities / kg_relations / kg_relation_evidence
```

查询：

```text
用户问题
  -> KnowledgeGraphRetriever
  -> 实体名称/别名匹配
  -> 一跳或二跳关系
  -> relation evidence
  -> knowledge_chunks
  -> RRF
```

所有图谱关系都应通过 `kg_relation_evidence.chunk_id` 回到原始 Chunk，
最终回答仍应以文档证据为准。

### 实体与关系在哪里定义

真正约束运行时代码的是 `rag/knowledge_graph/schemas.py`：

- 实体类型：`SYSTEM`、`MODULE`、`INTERFACE`、`REQUIREMENT`、
  `TEST_CASE`、`ROLE`、`ENVIRONMENT`、`DOCUMENT`、`VERSION`、
  `TERM`、`OTHER`。
- 关系谓词：`CONTAINS`、`PART_OF`、`DEPENDS_ON`、`CALLS`、
  `PROVIDES`、`IMPLEMENTS`、`SATISFIES`、`VERIFIED_BY`、
  `DEPLOYED_ON`、`OWNED_BY`、`USES`、`RELATED_TO`。

`rag/knowledge_graph/extractor.py` 把相同白名单写进抽取 Prompt，并负责
JSON、实体类型、关系谓词、`local_id`、自环和原文 evidence 校验。
完整的目标设计和字段解释见根目录
[知识图谱实施方案](../知识图谱实施方案.md)第 6、7、9、12、13、14 节。

`GraphBuildService` 会按 `GRAPH_MIN_CONFIDENCE` 过滤低置信度关系，并把
`GRAPH_SCHEMA_VERSION` 写入每个 Chunk。Schema 版本变化后，即使 Chunk
状态已经是 `completed`，也会自动重新抽取。`GraphExtractor.extract_batch()`
会把一批 Chunk 合并为一次 LLM 请求，而不是逐 Chunk 请求。

### 图谱结果怎样进入回答上下文

`KnowledgeGraphRetriever` 先找到实体及其一至二跳关系，再通过
`kg_relation_evidence.chunk_id` 取回原始 `knowledge_chunks`。三路 RRF
和 Reranker 处理后，`ContextBuilder` 把 `graph_facts` 和片段正文写入同一
段 `context` 文本。

当前传给回答 LLM 的不是独立的“文本上下文 JSON + 图谱子图 JSON”，而是
一个已经排版好的字符串。最终上下文可通过下面的配置导出：

```dotenv
CONTEXT_JSON_EXPORT_ENABLED=true
CONTEXT_JSON_EXPORT_DIR=data/debug/contexts
```

导出由 `rag/context/context_exporter.py` 完成，调用位置是
`rag/nodes/context_node.py` 和 `app/services/rag_service.py`。每次问答会
生成一个 JSON，包含原问题、改写问题、LLM 实际使用的 `context`、来源、
检索通道和图谱事实。该能力默认关闭，因为文件中包含业务知识片段。

## 8. Provider 边界

Provider 接口定义在 `rag/providers/interfaces.py`。

| 接口 | 当前实现 |
| --- | --- |
| `LLMProvider` | 智谱兼容 API、Ollama |
| `EmbeddingProvider` | Ollama Embedding |
| `Reranker` | BGE CrossEncoder、Passthrough |
| `VectorStoreProvider` | Chroma |

云端 LLM 缺少 URL 或 Key 时会回退到 Ollama。当前图谱抽取使用 `current`
并复用问答的 `glm-5.2` Provider。Embedding 默认始终依赖本地 Ollama，
`rag/providers/embedding.py` 使用 `/api/embed` 批量接口，因此即使回答使用
云端 LLM，Ollama 仍需运行。

## 9. 数据表

| 表 | 用途 |
| --- | --- |
| `users` | 登录用户 |
| `conversations` | 用户会话 |
| `messages` | 用户和助手消息 |
| `knowledge_documents` | 文档索引状态 |

| `kg_relation_evidence` | 关系对应的原文证据 |

模型变更必须同时检查 `app/models/`、`app/models/__init__.py` 和
`migrations/versions/`。

## 11. 验证顺序

```powershell
# 自动化测试
.\venv\Scripts\python.exe -m pytest -q

# 只检查文件变化，不写索引
.\venv\Scripts\python.exe -m scripts.ingest_documents --dry-run

# 查看 Chroma collections
.\venv\Scripts\python.exe -m scripts.ingest_documents --list-collections

# 启动 API
.\venv\Scripts\python.exe -m uvicorn app.main:app --reload
```

测试通过只能证明已覆盖的行为正确，不能替代真实索引数量一致性和评估验收。
