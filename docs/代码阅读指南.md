# 代码阅读指南

> 本指南基于当前代码结构（2026-08，Alembic Head `f2d6a8c1e4b7`，170 项测试 + 2 subtests 通过）编写。
> 系统总览、部署迁移和运维排障见 [系统总体说明](系统总体说明.md)。

## 1. 先理解三个入口

项目有三个主要入口，它们分别处理在线问答、离线索引和质量评估。

| 入口 | 文件 | 作用 |
| --- | --- | --- |
| HTTP 服务 | `app/main.py` | FastAPI 生命周期（迁移、初始化、租约恢复、Worker/Scheduler 启停）、中间件、异常处理和路由注册 |
| 文档索引 | `scripts/ingest_documents.py` | 同步、重建、collection 管理和图谱构建命令 |
| RAG 评估 | `scripts/evaluate_rag.py` | retrieval/full 评估及结果对比 |

第一次阅读代码时，建议按“API -> Service -> RAG Node -> Provider/Store”的方向阅读。

## 3. 在线问答：所有入口共用一份编译后的 LangGraph

与早期“Web 聊天手工编排”不同，当前**所有问答入口都执行同一份编译图**（`rag/graph/rag_graph.py`）：

```text
app/api/routes.py /ask                     ─┐
app/api/v1/knowledge_bases.py .../ask       ├─→ app/services/rag_service.py
app/api/v1/messages.py 同步消息 / SSE 流     ─┘       │
                                                     ├─ get_graph(kb_id)  [按索引签名缓存]
                                                     └─ graph.invoke(state) / graph.stream(state)
```

`rag_service.py` 按知识库与索引签名（`get_index_signature()`：活动 collection + schema 版本 + embedding/corpus 指纹 + updated_at）缓存编译图；签名变化自动重建。SSE 请求把 `generation_mode` 置为 `context`，图在 `build_context` 后结束，再由同一 Runtime 的 `llm.stream()` 流式生成。

## 4. 当前 LangGraph 工作流（11 个节点）

工作流定义在 `rag/graph/rag_graph.py`：

```text
route_request
  → rewrite
  → route_after_rewrite
  → embed_query
  → [text_retrieve | graph_retrieve | code_retrieve]   并行
  → fuse
  → rerank
  → build_context
  → generate（同步）/ END（SSE 上下文准备）
```

| 节点 | 文件 | 输入重点 | 输出重点 |
| --- | --- | --- | --- |
| `route_request` | `rag/nodes/route_node.py` | 原问题、显式通道、scope | `route`（通道、理由、置信度）、`allowed_document_ids` |
| `rewrite` | `rag/nodes/rewrite_node.py` | 原问题、历史、路由置信度 | 改写问题、`retrieval_queries` 列表 |
| `route_after_rewrite` | `rag/nodes/route_node.py` | 改写后问题 | 规则复核后的最终路由 |
| `embed_query` | `rag/nodes/embed_query_node.py` | 最终语义查询 | `query_embedding`（全链路只生成一次） |
| `text_retrieve` | `rag/nodes/channel_retrieval_nodes.py` | 检索问题列表、共享向量、策略 | `text_docs`、`text_channel_result` |
| `graph_retrieve` | 同上 | 同上 | `graph_docs`、`graph_channel_result` |
| `code_retrieve` | 同上 | 同上 | `code_docs`、`code_channel_result` |
| `fuse` | 同上（fusion_node） | 三通道候选 | `retrieval_candidates`（按 chunk_id 去重） |
| `rerank` | `rag/nodes/rerank_node.py` | 原问题、候选 | `docs`（Top-K 重排） |
| `build_context` | `rag/nodes/context_node.py` | docs | `context`（Token 预算、来源配额）、`sources` |
| `generate` | `rag/nodes/generate_node.py` | 原问题、历史、上下文 | `answer` |

要点：

- 三个通道节点**写各自独立的状态字段**（`text_docs`/`graph_docs`/`code_docs` 与 `*_channel_result`），并行无冲突；单通道失败记录在通道结果里，不阻塞其余通道。
- `route_request` 内的范围解析由 `rag/retrieval_scope.py` 完成：tag/folder/metadata 先解析为当前知识库允许的文档 ID 集合，再下推各通道。
- 三档策略由 `rag/retrieval_strategy.py` 统一提供：fast 减半 K 值并固定 1 跳；standard 用默认值；deep 翻倍 K 值、2 跳、扩大上下文预算。
- 路由规则在 `rag/routing.py`：显式通道 > 关键词规则（关系/依赖/影响→graph；代码/函数/调用→code；默认 text）> 可选 LLM 回退（`ROUTER_LLM_ENABLED`，默认关）。

## 6. 检索链路

`RAGRuntime`（`rag/runtime/runtime.py`）在首次提问时按知识库加载，索引签名变化自动失效重建：

```text
answer/rewrite LLMProvider（四角色独立配置）
EmbeddingProvider
Reranker（BGE / HTTP / Passthrough）
活动 Chroma collection
HybridGraphRetriever（向量 + BM25 [+ 图谱]）
KnowledgeGraphRetriever / CodeGraphRetriever
```

一次检索的主要步骤：

1. `route_request` 解析通道与文档范围。
2. `rewrite` 仅在置信度 < 0.75 或多轮时调用 LLM，产出 `[original_query, rewritten_query]`。
3. `embed_query` 生成唯一共享问题向量。
4. 文档通道对每个查询执行 Chroma 向量 + 中文 BM25，加权 RRF 融合。
5. 图谱通道并行执行实体词法/向量召回、关系词法/向量召回；关系候选作为 0 跳事实，端点扩展 1～2 跳遍历，经 `kg_relation_evidence` 回链 Chunk。
6. 代码通道对活动快照做 Symbol 词法/结构向量/功能摘要向量 RRF 召回，再扩展 calls/imports/extends。
7. `fuse` 跨通道加权融合并按 `chunk_id` 去重。
8. Reranker 以原始问题重排 Top-K。
9. ContextBuilder 施加来源配额（每源 ≤2 Chunk）与 Token 预算（默认 3000 × 0.85）。

## 7. 文档索引链路

```text
CLI/API/数据源
  -> DocumentIndexService（创建持久化任务，幂等去重）
  -> IndexJob + IndexJobItem
  -> IndexWorker（本地线程或 Celery；租约领取 + 心跳续约）
  -> DocumentIndexService / IndexManager
  -> Loader（按扩展名）
  -> Chunker（递归切分 + tiktoken 计数）
  -> Chroma + knowledge_documents + knowledge_chunks
```

核心数据标识：

- `document_id`：文档 UUID。
- `file_hash`：文件内容 SHA-256。
- `chunk_id`：由 document_id、file_hash、INDEX_SCHEMA_VERSION（当前 2）和序号确定性生成。
- `active_collection_name`：保存在 `knowledge_index_state`。

全量重建先写入影子 collection（`documents_build_{job_id}`；多知识库为 `documents_{kb短id}_build_{job_id}`），数量和 ID 全部校验通过后才在一个事务中替换 Chunk 并切换活动指针。单文件更新先写新向量和数据库，再清理旧向量；失败时旧索引保持可用。任务租约默认 300s、心跳 30s、最多重试 3 次；API 启动时执行 `recover_expired_leases()` 恢复过期任务。

## 8. 知识图谱链路

构建：

```text
自动（索引成功后防抖触发）或手动（治理页快速/标准/深度）
  -> GraphSchemaInductionService（采样归纳 Schema 草稿，必须人工激活）
  -> GraphBuildService
  -> pending KnowledgeChunk（规则预过滤跳过无事实 Chunk）
  -> GraphExtractor（活动 Schema 的实体/关系字典写入 Prompt 并校验输出）
  -> extraction LLM（默认复用 answer 配置，可独立覆盖）
  -> Pydantic / evidence / 置信度校验（GRAPH_MIN_CONFIDENCE=0.60）
  -> SqliteGraphStore（SQLAlchemy，SQLite 或 PostgreSQL 同一实现）
  -> kg_entities / kg_relations / kg_relation_evidence
  -> 实体向量 + 关系向量（版本化 Collection）
```

查询（在 `graph_retrieve` 节点内）：

```text
用户问题
  -> 实体名称/别名词法匹配 + 实体向量召回
  -> 关系谓词/中英文别名词法 + 关系向量召回
  -> 种子合并；关系作 0 跳事实，端点扩展 1～2 跳
  -> relation evidence -> knowledge_chunks
  -> 通道内 RRF
```

所有图谱关系都通过 `kg_relation_evidence.chunk_id` 回到原始 Chunk，最终回答仍以文档证据为准。

### Schema 与实体/关系定义

- 运行时白名单兜底在 `rag/knowledge_graph/schemas.py`：实体类型 `SYSTEM`、`MODULE`、`INTERFACE`、`REQUIREMENT`、`TEST_CASE`、`ROLE`、`ENVIRONMENT`、`DOCUMENT`、`VERSION`、`TERM`、`OTHER`；关系谓词 `CONTAINS`、`PART_OF`、`DEPENDS_ON`、`CALLS`、`PROVIDES`、`IMPLEMENTS`、`SATISFIES`、`VERIFIED_BY`、`DEPLOYED_ON`、`OWNED_BY`、`USES`、`RELATED_TO`。
- 实际构图优先使用**活动 Schema**（`graph_schema_definitions`）中定义的实体/关系类型与抽取规则；`GraphExtractor.extract_batch()` 会把一批 Chunk（默认 6 个）合并为一次 LLM 请求。
- 每个知识库的五类图谱分别最多一个活动 Schema：激活只把同类旧版本置 `superseded`，数据库部分唯一索引（迁移 `d3f1b8a690ce`）拒绝同类并发激活；构图时五套约束合并为一次抽取。
- 人工校正（改名/隐藏/新增关系）以 Overlay 存于 `kg_graph_corrections`，查询时叠加生效，可回退；实体/关系消歧合并分别存 `kg_entity_merges` 与合并后的关系记录，保留审计。

### 图谱结果怎样进入回答上下文

`KnowledgeGraphRetriever` 召回的图谱事实与证据 Chunk 一起进入通道候选；跨通道融合与重排后，`ContextBuilder` 把图谱事实与片段正文排版进同一段 `context` 文本。最终上下文可导出排查：

```dotenv
CONTEXT_JSON_EXPORT_ENABLED=true
CONTEXT_JSON_EXPORT_DIR=data/debug/contexts
```

导出由 `rag/context/context_exporter.py` 完成，调用位置是 `rag/nodes/context_node.py` 和 `app/services/rag_service.py`。每次问答生成一个 JSON，包含原问题、改写问题、LLM 实际使用的 `context`、来源、检索通道和图谱事实。该能力默认关闭，因为文件中包含业务知识片段。

## 9. 代码图谱链路

```text
Git / 本地目录连接器同步
  -> CodeIndexService
  -> 相对路径 + SHA-256 差异分类（新增/修改重解析；未变化复用；删除剔除）
  -> CodeParser（Python ast；其他语言 Tree-sitter + 规则 emitter）
  -> code_files / code_symbols / code_relations（版本化快照，原子激活）
  -> CodeVectorService（结构向量 + 功能摘要向量，稳定 vector_kind+stable_key ID）
```

检索时 `CodeGraphRetriever` 做 Symbol 词法 + 双向量 RRF 召回，再扩展调用/依赖关系。快照默认保留 3 个；Parser 版本或数据源变化自动全量重解析；Embedding 指纹变化触发影子全量重建。

## 10. Provider 边界

接口定义在 `rag/providers/interfaces.py`；工厂与角色路由在 `rag/providers/factory.py`。基础设施契约（对象存储/队列/缓存/会话）在 `app/adapters/interfaces.py`，由 `app/bootstrap/container.py` 组装并做 enterprise Profile 校验（指向本地适配器直接失败）。

| 接口 | 当前实现 |
| --- | --- |
| `LLMProvider` ×4 角色 | answer / rewrite / router / extraction；智谱兼容、OpenAI-compatible、Anthropic 兼容、Ollama |
| `EmbeddingProvider` | Ollama（`/api/embed` 批量）、OpenAI-compatible |
| `Reranker` | BGE CrossEncoder（进程内）、HTTP `/v1/rerank`、Passthrough |
| `VectorStoreProvider` | Embedded Chroma、Chroma HTTP |
| `GraphStore` | SqliteGraphStore（SQLAlchemy，SQLite/PG 同一实现） |
| `ObjectStoreProvider` | 本地目录、S3/MinIO |
| `TaskQueueProvider` | Inline（进程内唤醒）、Celery |
| `CacheProvider` | Memory、Redis |

本地 Profile 云端 LLM 缺 URL/Key 时回退 Ollama；enterprise Profile 直接启动失败。Embedding 默认依赖本地 Ollama，即使回答使用云端 LLM，Ollama 仍需运行（除非配置远程 Embedding）。
